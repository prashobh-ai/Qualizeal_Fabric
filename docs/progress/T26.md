# T26 — Two-turn context window + coreference resolution

A follow-up question rarely repeats its subject — "what about its pricing",
"and for testers?", "the second one". Before T26 those dropped to a gap or an
answer to the wrong question. Now the answer service resolves the follow-up
from the last one or two turns, rewrites it, and only then retrieves — or asks
back with chips when the reference is genuinely ambiguous. It is deterministic,
model-free, and resolves identically on the server and in the static showcase.

## The resolution ladder

`knowledge_fabric/answer/context.py` → `resolve(question, turns, subjects)`
returns a `Resolution(question, understood_as, clarify)`. In order:

1. **Clarify option** — the previous turn asked back and this question is one of
   its offered options → re-ask the *original* question with that option
   substituted ("QMentisAI" after a "which one?" clarify → "when was QMentisAI
   made").
2. **Comparative** — "what about &lt;entity&gt;" that names its *own* new entity →
   swap it into the previous question's intent ("what about NexaAI" after "what
   does QMentisAI do" → "what does NexaAI do"). Checked before the
   self-contained short-circuit, since the follow-up names a new subject.
3. **Self-contained** — a question that already names a subject passes through
   unchanged (no `understood_as`).
4. **Ordinal** — "the second one" → the matching document of the last answer.
5. **Pronoun / possessive** with no entity of its own → substitute the sticky
   subject ("what about its pricing" → "what about QMentisAI pricing").
6. **Ellipsis** with no verb ("and for testers?", "for QA") → subject + tail,
   reaching up to **two turns back** for the sticky subject.

When a pronoun or a compare-intent has no subject to resolve to, it returns a
**clarify** with 2–3 subject chips instead of a blind rewrite; clicking a chip
re-asks the original question (rule 1).

The subject vocabulary is the distinctive-title tokens that name exactly one
document, filtered to product/brand entities (an internal capital: QMentisAI,
ValidAIte) — the same rule the showcase subject vocabulary uses — so
coreference stays clean and never latches onto a generic word. `subject_in`
matches **whole tokens**, never a substring, so "testers" does not resolve to a
"test" subject; latest mention wins.

## Wiring

- `AnswerService.ask(principal, question, context=...)` is the public entry: it
  runs the ladder, returns a clarify (with `suggestions` chips) when ambiguous,
  else calls the answer path on the rewritten question and stamps
  `answer.understood_as`. `_answer` is the former body, unchanged.
- The `Answer` contract carries `understood_as` and `suggestions`, both in
  `to_dict()`.
- `POST /ask` passes `context` through from the request body.
- The Workspace client sends a rich two-turn `context.turns`
  (`{question, kind, answer_docs, options}`) and renders `understood_as` as a
  small italic "understood as: …" line under the question bubble when a rewrite
  happened. Clarify chips ask their question on click.

## Static-showcase parity

`scripts/showcase/engine.js` → `resolveCtx` is a line-for-line port of the
Python ladder over `SNAP.subjects` and the client-sent `context.turns`. The
rewritten question flows through the same `lookup` (baked cache) → `retrieve`
(browser BM25) path, so a follow-up resolves on GitHub Pages exactly as on the
server. A Node harness drives the *shipped* `resolveCtx` block and the Python
`resolve` through eight identical scenarios — self-contained, pronoun, ellipsis
two-turn reach, comparative, empty-"it" chips, ordinal, clarify-option click,
compare-no-entity — and they agree byte-for-byte.

## Deferred (later Tnn)

Longer context windows (beyond two turns), entity-linking across a whole
session, and multi-subject comparisons in one turn ("compare QMentisAI and
ValidAIte" answered as a table) — T26 covers two-turn coreference and the
ask-back, which is what the demo needs.
