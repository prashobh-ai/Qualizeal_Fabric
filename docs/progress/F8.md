# F8 — GitHub-ready demo: the interactive Pages showcase
Status: DONE

The whole product now runs on GitHub Pages as a static, role-based, interactive
demo — no server — plus a scheduled ingestion check. This closes the
"demo-ready from the GitHub side" ask.

## How it works (browser-side engine)

GitHub Pages is static, so the showcase serves the REAL product surfaces and
answers every API call in the browser:

- **`scripts/build_showcase.py`** seeds an in-memory fabric with the
  self-contained demo corpus, drives a realistic question spread across roles
  (populating telemetry, analytics, usage and cache), then starts the real HTTP
  handler in-process and captures the ACTUAL JSON every endpoint returns, per
  role, into `snapshot.json`. It emits each surface's real HTML into its own
  folder with `/static` rewritten to relative paths and `engine.js` injected
  before the runtime, and writes the landing page at the root.
- **`scripts/showcase/engine.js`** intercepts `window.fetch` and serves the
  snapshot: sign-in, `/ask` (nearest baked answer), galaxy, usage, analytics,
  and all curator/admin reads. POST mutations (curator decisions, add/remove
  user, feedback) update a client-side copy of the state, so the demo is
  genuinely interactive. It also derives the deploy base from the URL so one
  build serves the Pages repo path, localhost, or an AWS subpath.

## What's live on the showcase

- **Landing** (`index.html`) — brand hero, the four reader levels, the
  explainability story (level · why · galaxy) and the governed 5-step path, role
  cards, and a **bottom-left chatbot** that answers from the baked bank.
- **Sign-in** — role picker (Asker · Restricted asker · Curator · Admin).
- **Workspace** — the full L2 chat: threads, corpus strip, grounded answers with
  citation chips + page viewer, the card, the answer galaxy + Explain, My usage,
  and a **👍/👎 feedback** control.
- **Admin** — connectors/sync, runs, bulk load/delete, **Users & Access with
  add/remove user**, budgets, audit, and cloud-readiness (doctor).
- **Curator** — data-quality dashboard, risk register, curation queues (gaps,
  contradictions, low-confidence review), the **User feedback to check** queue
  (fed by Workspace 👎), the documents table with filters + keep/delete/mark
  authoritative/rollback, add-a-document, and authority ranks.
- **Telemetry** — the six-tab analytics dashboard (Overview · Trust · Sources ·
  Models · Usage · Cost & Caching) over the baked analytics.

## App changes that made it portable

- **`ui_common.py`** — a runtime `KF_BASE` (deploy base) and `KF_ROUTES` (folder
  remap) indirection; nav links carry `data-path` and are prefixed on load. All
  default to identity, so the Python server is unaffected. This also makes the
  app deployable under any subpath (AWS included).

## New product features (server + UI, work on the laptop deploy too)

- **Users & Access** — `POST /admin/users` add/disable a demo user (admin-only);
  the Admin UI grew an add-user form and per-row Remove.
- **User feedback loop** — `POST /feedback` records a reader's 👎 into the
  curation queue as `negative-feedback`; `GET /curator/feedback` lists it; the
  Workspace answer carries 👍/👎 and the Curator shows the review queue.

## Scheduled GitHub Actions

- **`.github/workflows/ingestion-check.yml`** (new) — daily cron + manual: runs
  the doctor, the full ingest via the showcase build, the static verifier, the
  routing eval, and the ingestion/showcase/UI tests; uploads the snapshot.
- **`.github/workflows/showcase.yml`** — now builds and deploys the real
  interactive showcase (was a placeholder).

## Verification

- Driven end-to-end in Chromium against the built static site under a base path:
  landing + chatbot, sign-in, Workspace (answer, galaxy 22 nodes, chips, page
  viewer, Explain, feedback), Admin (user add 5→6→5), Curator (feedback queue
  fed by 👎), Telemetry (58 answers, 6 tabs, 8 KPIs) — **zero JS errors**.
- Full suite **303 / 303**; `tests/test_showcase.py` rewritten for the
  interactive build (structure, snapshot per-role, engine injection, no external
  URLs); `verify_showcase.py` extended to require the snapshot + surfaces.

## Deferred (not needed for the demo)

- Threads and demo mutations are per-session/client on Pages (real persistence
  is the server/AWS deploy).
- The real QualiZeal `.docx` corpus is not in the repo; the showcase uses the
  self-contained demo corpus. `scripts/load_qualizeal_corpus.py` loads the real
  one on a laptop when the documents are present.
