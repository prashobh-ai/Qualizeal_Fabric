# T32 — Static parity (the showcase answers like the server)

The static showcase runs on GitHub Pages with no server: `engine.js`
re-implements the answer path — coreference, persona conditioning, retrieval,
discovery, the answer shape — over a baked snapshot. Two implementations of one
behaviour drift. `verify_showcase` already checked the build's *structure* (files
present, no external URLs, snapshot has answers); T32 adds the missing guard —
that the mirror stays **behaviourally faithful**.

## How it proves parity

`scripts/parity_check.py` runs the **actual shipped `engine.js`** — not a
re-implementation — against the Python server:

1. Seeds a small fabric (products, code + its test, an auth helper, an SSO
   policy) and drives a curated set of questions through the real
   `AnswerService`.
2. Bakes a **production-shaped snapshot** (the exported retrieval index, the
   subject vocabulary, and the server's answers under the engine's lookup key).
3. Runs `scripts/showcase/parity_runner.js` — a minimal browser shim
   (window / location / localStorage / snapshot-serving fetch) that loads the
   real `engine.js` and drives it exactly as the Workspace would: **POST /login,
   then POST /ask** per case.
4. Compares the two answers on every reader-visible classification.

The engine **re-computes** the two parity-risk behaviours client-side on top of
the baked answer — the coreference rewrite (`understood_as`, T26) and the persona
lens (`role_view`, T27) — so comparing those against the server is a real test,
not a snapshot round-trip.

## What must match (and what may not)

Per question, server and engine must agree on:
- **kind** — answer / clarify / gap,
- **understood_as** — the coreference rewrite (T26),
- **role_view** — persona lens / persona / depth / emphasis (T27),
- **cited / discovery / code** shape.

Answer-derived numbers that legitimately differ between the model-free static
composer and the server — exact prose, grounding score, per-source counts,
cost — are **not** compared. Parity is on the classification the reader sees,
not on byte-identical text.

## The cases

`self.{developer,cto,tester,general,curator}` (persona lens across designations),
`coref.pronoun` and `coref.reach` (two-turn coreference, the second reaching two
turns back), `code`, `discovery`, `decline`, and `clarify.empty` (a bare pronoun
with no session asks back). All 11 agree.

## Where it runs

- **`make parity`** — the local one-liner.
- **`.github/workflows/ci.yml`** — a *Static parity (T32)* step in the `mcp` job,
  which already sets up Node.
- **`tests/test_t32_parity.py`** — runs the end-to-end check when Node is present
  (skips cleanly otherwise) and unit-tests the comparison contract without Node.

## Done-when

- The real `engine.js`, driven like the browser over a production-shaped
  snapshot, agrees with the Python server on kind, coreference, persona lens,
  and cited/discovery/code shape for every case. ✓
- The check fails loudly on divergence (the comparison unit tests prove a lens
  or coreference drift is caught). ✓
- `make parity` / the CI step exit non-zero on drift. ✓

## Verified

`tests/test_t32_parity.py` (5: the comparison contract catches lens and
coreference drift; `_norm` matches the engine key; the end-to-end check passes
with 11/11 cases agreeing). `python scripts/parity_check.py` → PASS; full suite
green; `ruff` clean.

## Deferred (later Tnn)
