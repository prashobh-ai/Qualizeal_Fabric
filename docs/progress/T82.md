# T82 — Known-question registry per persona

The business slice depends on a curated set of instant, governed questions. This
generalises it to every audience: each persona has its own set of "questions the
fabric answers instantly", governed and maintained by the Curator.

## What it is

- **`answer/registry.py` + `answer/known_questions.json`** — a governed list of
  question patterns, each `{id, pattern, persona[], answer_kind, source,
  template, freshness_target_s, examples[], enabled}`. The seed ships in the
  package (repo convention for authored governed data, like
  `telemetry/prices.json`); a curator's edits persist to the fabric-data runtime
  file `data/known_questions.json` (honouring `KF_DATA_ROOT`) and, once written,
  that file is the whole registry. It is **metadata, not a new engine** — every
  entry resolves through the existing facts and retrieval paths.
- Starter sets cover the article's audiences: business / sales / delivery,
  developer, tester / quality, architect, curator / admin, HR / people. A
  persona is fanned out to its registry **audiences** (`AUDIENCES_FOR`) — a
  developer and an architect share the `developer` answer-persona but are
  offered different instant questions.

## The three things the registry drives

1. **Per-persona suggested questions on Home.** `GET /api/suggestions` now
   returns `persona` and a `known` list drawn from the reader's registry
   audiences, alongside the existing ACL-gated tenant bank. The Workspace Home
   leads with an "Answered instantly · &lt;persona&gt;" strip, then the corpus
   suggestions.
2. **A fast-path lock.** `AnswerService._answer` matches the resolved question
   against the registry (`Registry.match`, persona-agnostic — a governed
   question is instant for anyone). A match never decomposes and never
   escalates: the selector level is capped at the fast path and a
   `known_question` reason is stamped on the why-card and telemetry, so a
   curated question's time-to-answer stays a commitment.
3. **A governed list the Curator maintains.** Curator → Registry: view every
   entry with its personas, answer kind, source and freshness target; add or
   edit a known question; disable one without deleting it. `GET /curator/registry`
   reads it; `POST /curator/registry {action: upsert|enable|disable}` writes it.
   Every change is audited (`registry:upsert` / `registry:enable` /
   `registry:disable`) and takes effect for its persona immediately.

## MCP (T89)

`list_known_questions(persona?)` returns the registry so an agent can offer a
user their instant questions — the whole enabled set, or one audience's entries
plus a ready-to-ask suggestion list.

## Showcase

`/api/suggestions` is baked per role (keyed by subject, scope-key fallback) so
each persona's static Home shows its own known questions; the known examples are
folded into the answer bake so a known chip resolves model-free. `/curator/registry`
is baked into the curator bucket and served by the engine; a write in the static
demo is acknowledged without server-side state, as with the other curator writes.

## Verification

`tests/test_registry.py`:

- **match** — a free-text question resolves to the most specific entry; a
  question the registry does not cover returns `None` (never forced onto the
  fast path); a persona filter narrows correctly.
- **suggestions** — every persona has suggestions, and they differ by persona.
- **fast-path lock** — every known example resolves with `tier ∈ {none, fast}`
  and level ≤ 2; a grounded known question stamps the `known_question` reason.
- **curator CRUD** — an add persists and is offered to its persona; a disable
  retires a question (still present, no longer matched or suggested) without
  deleting it; an add without id/pattern is rejected.
- **MCP** — `list_known_questions` returns per-persona and whole-registry views.

Full `pytest` stays green; `ruff` check + format clean; static parity green;
`make showcase` builds clean.
