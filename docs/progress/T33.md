# T33 — Load test (the answer path under concurrent load)

The concurrency-correctness test (`tests/test_concurrency.py`) proves the
*correctness* invariants under threads — no cross-tenant leakage, unique
trajectories, no request-context bleed. T33 adds the missing *performance*
guard: how the governed answer path behaves under sustained concurrent load,
gated against SLOs so a throughput or latency regression fails loudly instead of
quietly bleeding into production.

## What it measures

`scripts/load_test.py` builds a small fabric (two products, two code files),
mints many distinct asker principals, and fires a mixed workload — a definition,
a code look-up, an asset-discovery, a multi-fact question and an out-of-corpus
decline — across a thread pool. It runs on the **model-free extractive path**
(the deployed floor), so it is deterministic and needs no credits.

It runs the same load **twice**:

- **cold** — a fresh answer cache,
- **warm** — the identical load again, now served largely from the answer cache.

Per phase it records QPS, latency percentiles (p50/p95/p99/max/mean), and
outcome counts (ok / error / throttled / declined / distinct trajectories).

## The gate (SLOs)

A run **fails** (non-zero exit) on any of:

- **errors** — any unhandled exception on the answer path,
- **throttled** — any request hit the per-user rate limit (the load is spread
  across enough principals that the limiter never dominates; a throttle here
  means the spread broke, not that the path is slow),
- **trace bleed** — `distinct_traces != answered`, i.e. two concurrent requests
  shared a trajectory id,
- **p95 latency** over the SLO,
- **QPS** under the SLO floor,
- **cache regression** — the warm run is materially slower than cold
  (`warm_qps < 0.9 × cold_qps`), which would mean the answer cache stopped
  helping.

```
SLO = {"p95_ms": 750.0, "min_qps": 20.0}
```

These carry deliberate headroom over measured values (see below) so the gate
flags a real regression, not normal CI-runner variance.

## Why many principals

Each simulated user carries its own 60/min rate-limit budget. A realistic
"many users at once" burst spreads the load across a pool sized so that **both**
phases together stay under the per-user limit (`requests // 20` principals →
~40 asks/user across cold+warm, comfortably under 60). This tests the answer
path's throughput, not the rate limiter — which is exercised separately.

## Measured (local, this environment)

```
400 req × 12 workers — PASS
  cold: ~396 qps · p50 20ms · p95 68ms · p99 113ms · errors 0 · throttled 0 · traces 400/400
  warm: ~432 qps · p50 20ms · p95 63ms · p99 69ms · errors 0 · throttled 0 · traces 400/400

1000 req × 24 workers — PASS
  cold: ~424 qps · p50 40ms · p95 127ms · p99 193ms · errors 0 · throttled 0 · traces 1000/1000
  warm: ~446 qps · p50 39ms · p95 124ms · p99 142ms · errors 0 · throttled 0 · traces 1000/1000
```

Zero errors, zero throttles, every answered request its own trajectory, warm ≥
cold throughput — and p95 an order of magnitude under the 750ms SLO.

## Where it runs

- **`make load`** — the local one-liner
  (`python scripts/load_test.py [--requests N --concurrency K] [--json]`).
- **`tests/test_t33_load.py`** — a small end-to-end burst (fast, deterministic)
  plus unit tests of the percentile + breach logic, including a *gate-has-teeth*
  test that an unreachable SLO actually fails the run.

The full 400-request burst is not put on the CI critical path (it is a
performance probe, not a correctness gate, and runner throughput varies); CI
runs the fast in-process burst via the test suite, and the standalone script is
the tool for a deliberate load probe.

## Done-when

- The answer path sustains concurrent load with zero errors, zero throttles, and
  a unique trajectory per answered request. ✓
- Latency percentiles and throughput are measured and gated against SLOs with
  headroom. ✓
- The warm cache demonstrably does not regress throughput. ✓
- The gate exits non-zero on breach, and a unit test proves the gate is enforced,
  not cosmetic. ✓

## Verified

`tests/test_t33_load.py` (5: percentile buckets; empty-safe; report PASS/FAIL
rendering; a small burst meets every SLO with unique traces; a tightened SLO
actually fails the run). `python scripts/load_test.py` → PASS at 400×12 and
1000×24; full suite green; `ruff` clean.

## Deferred (later Tnn)

A sustained soak (fixed duration rather than a fixed request count) to surface
slow leaks; load against the Postgres-backed store once the repository adapter
ships; and a latency-budget breakdown by stage (retrieval / grounding / compose)
so a regression points at the offending stage.
