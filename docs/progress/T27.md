# T27 — Role-conditioned answers (by organisational designation)

The same question, asked by different people, should land differently — a
developer wants the implementation in full, a tester wants what verifies it, a
delivery lead wants a brief status, a CxO wants the headline. T27 conditions the
answer on the asker's **organisational designation** without ever changing the
grounded facts.

## The rule that keeps it honest

A person's role here is their **designation** — developer, tester, QE, architect,
manager, delivery head, director, CTO — captured by the **admin when the user is
added** (it rides `Principal.designation`, minted into the token), **not** chosen
on the ask window. The designation conditions *framing*; it never widens what is
retrievable — that is `scopes`/ACL, enforced before ranking (invariant I6). A
developer with public-only scope still cannot see restricted material.

## Personas — the conditioning axis

`knowledge_fabric/answer/personas.py` is the single source of truth. It maps the
many titles a company uses onto a small set of personas, each with a
deterministic, model-free profile:

| Persona | Titles (examples) | Depth | Emphasis | Lens |
|---|---|---|---|---|
| **builder** | developer, architect, DevOps, SDE | full (3) | code | builder |
| **quality** | tester, QE, SDET, automation | full (3) | test | quality |
| **delivery** | manager, delivery head, scrum master | brief (2) | authority | delivery |
| **executive** | director, VP, CEO, CTO | headline (1) | authority | executive |
| **curation** | curator, knowledge manager | full | — | curation |
| **operations** | admin, platform, SRE-ops | full | — | operations |
| **general** | (no designation) | full | — | answer |

## What the persona changes (three levers, all model-free)

1. **Emphasis** — `_persona_boost` gently lifts the grounded evidence the persona
   cares about (a soft tie-breaker, a fraction of the top score, applied after
   authority + subject boosts), and the code composer honours it too. A developer
   asking "how does `retry_call` work" leads with `retry.py`; a tester leads with
   `test_retry.py`. Same grounded question — persona-relevant evidence first.
2. **Depth** — composition caps the answer at the persona's sentence budget:
   headline (1) for an executive, brief (2) for delivery, full (3) for builders,
   quality, curators, admins and the general reader. The facts stay grounded and
   cited; the persona only decides how much of the grounded answer is surfaced.
   The full answer cache is keyed per persona (`_answer_scope`), so the first
   reader's framing is never served to another designation.
3. **Lens** — `_persona_view` stamps a `role_view` frame on the finished answer:
   the persona note, its depth and emphasis, plus the governance frame for
   curators (grounding, sources, a single-source gap hint) and the operations
   frame for admins (level, model, cost, cache, tokens).

The `Answer` contract carries `role_view` (in `to_dict`). The admin **add-user**
form and API capture the designation; the directory row is
`(subject, roles, scopes, designation)`, unpacked tolerantly by
`demo.user_fields`.

## Static-showcase parity

`scripts/showcase/engine.js` mirrors it verbatim: `personaFor` + `PERSONA_PROFILE`
(the same title→persona map and profiles), `roleView` (a field-for-field port of
`_persona_view`), and persona depth + emphasis in the browser retrieval/compose.
The signed-in identity's designation drives it — `designationOf` reads it from
the login (admin@/curator@ seeds, or a demo local-part like
`developer@qualizeal.com` / `cto@qualizeal.com`), never a picker. A Node harness
feeds the Python `_persona_view` outputs into the shipped `roleView` for all
seven personas and they agree byte-for-byte.

Static limitation (documented, honest): a *baked* answer is composed once and is
persona-agnostic, so on the static demo the **lens** always differs per persona
and **live** (unbaked) questions additionally show depth + emphasis; the server
applies all three to every answer.

## Done-when

- The admin captures a designation when adding a user; it rides the principal. ✓
- Same question, different designation → same grounded facts, different emphasis
  (dev leads with impl, tester with the test), depth (CxO headline → builder
  full) and lens. ✓
- The designation frames the answer; it never widens access. ✓

## Verified

`tests/test_t27_roles.py` (11 tests: the title→persona map, depth cap, emphasis
reorders the lead by persona, depth shapes length, a lens per persona, facts
stay grounded + cited for every persona, curator single-source gap hint, admin
operations fields, `role_view` serialises, the per-persona answer cache is
isolated, and a designation never widens access). Full suite green; `ruff` clean;
`verify_showcase` passes; a Node parity harness confirms the browser lens matches
the server across all personas.
